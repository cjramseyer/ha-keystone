# Multi-Application License Portal Implementation Plan

## Purpose

Build a low-cost licensing portal for multiple self-hosted applications. Each application is represented by an application profile that defines its identity, plans, features, limits, signing configuration, and activation rules. The portal should issue 30-day trial licenses and paid Pro licenses while allowing each application to validate paid licenses offline.

The portal must never place the private signing key in a public application repository or inside a customer installation.

## Application Profiles

Every application supported by the portal must have an application profile. The profile is the boundary between products and prevents one application's plans, features, limits, or license tokens from being accepted by another application.

An application profile should contain:

- Stable application ID, such as `bartender` or `another-app`
- Display name and optional logo/branding metadata
- Current and supported application versions
- Available plans, such as `base`, `pro`, or product-specific tiers
- Feature entitlement identifiers
- Plan-specific limits
- Trial duration and trial policy
- Installation and activation rules
- Token audience or application binding value
- Public verification key set and active signing key ID
- Billing product and price references
- Support and documentation URLs

Example profile:

```json
{
  "app_id": "bartender",
  "name": "BarTender",
  "plans": ["base", "pro"],
  "trial_days": 30,
  "features": ["pos_sync", "advanced_analytics", "multiple_displays"],
  "installation_limit": 2,
  "token_audience": "bartender",
  "active_key_id": "bartender-signing-2026-01"
}
```

The portal's first-class workflow should therefore be `application profile -> customer -> license`, not simply `customer -> license`.

## Required Instance Information for Issuance

Issuing a license must require information that identifies the specific application instance. A customer should not be able to request a license using only an email address or an application name.

Each application profile defines an instance-information contract. The contract should include:

- A human-readable value configured inside the application
- A unique instance identifier generated by that installation
- A public instance key or equivalent cryptographic identity
- A proof that the request was created by that application instance

For BarTender, the initial contract could require:

- The brewery name entered during first-run setup
- A unique instance key generated and stored by that BarTender installation
- An instance information string or activation request exported from BarTender

The brewery name provides a recognizable customer-facing binding, while the unique instance key provides the actual instance identity. The brewery name must not be treated as a secret because it can be guessed or shared.

The portal should display the required fields for each application profile and reject license requests that do not include all required instance information. The licensing workflow should show the customer exactly where to find these values in the application.

## Recommended Product Model

### Base

The free Base plan provides the core application with practical limits. Candidate limits include:

- Limited taps, displays, or active inventory capacity
- Basic analytics and history retention
- Basic backup and restore
- Manual workflows
- A single administrator or limited team access

### Pro

The paid Pro plan removes Base limits and enables premium capabilities. Candidate features include:

- POS integrations
- Multiple displays
- Advanced analytics and forecasting
- Higher or unlimited taps and kegs
- Extended audit and history retention
- Advanced menu branding
- Automated backups
- Expanded external API functionality
- Multi-user and role features where applicable

Feature names should be represented as stable entitlement identifiers, not scattered plan checks. Example identifiers:

- `pos_sync`
- `advanced_analytics`
- `multiple_displays`
- `extended_history`
- `automated_backups`
- `advanced_branding`

## Cheapest Effective Rollout

### Phase 1: Manual, Near-Zero Operating Cost

Start with a private issuer tool and hosted payment links:

1. Use Stripe Payment Links or Lemon Squeezy for payment.
2. Confirm payment manually.
3. Run the private issuer tool locally.
4. Generate a signed license token.
5. Send the token to the customer.
6. The application verifies and stores the token locally.

This avoids hosting, database, and uptime costs while the product and pricing model are being validated.

### Phase 2: Hosted Automation

When manual issuance becomes inconvenient, deploy the portal as:

- Cloudflare Worker for the API
- Cloudflare D1 for customer, license, and activation records
- Cloudflare Secrets or a KMS for signing-key operations
- Stripe or Lemon Squeezy webhooks for automatic payment handling
- Cloudflare Access or an equivalent protected admin interface

Render or Railway are acceptable alternatives if a traditional Python service and PostgreSQL are preferred. The hosted service should not be required for normal paid-license validation.

## License Format

Use an asymmetric signature scheme such as Ed25519.

- The portal owns the private signing key.
- The application contains only the public verification key.
- The portal signs license payloads.
- The application verifies the signature locally.

A signed JWS/JWT or signed JSON document is acceptable. The payload should contain data similar to:

```json
{
  "license_id": "lic_12345",
  "app_id": "bartender",
  "profile_id": "app_profile_12345",
  "customer_id": "cust_12345",
  "instance_binding": {
    "brewery_name": "Example Brewery",
    "instance_key_id": "instance-key-abc123",
    "instance_public_key_sha256": "base64url-hash"
  },
  "installation_id": "optional-installation-id",
  "plan": "pro",
  "license_type": "paid",
  "features": [
    "pos_sync",
    "advanced_analytics",
    "multiple_displays"
  ],
  "issued_at": "2026-09-13T00:00:00Z",
  "expires_at": "2027-09-13T00:00:00Z",
  "installation_limit": 2,
  "key_id": "signing-key-2026-01"
}
```

The application must verify both the signature and the application audience/profile before accepting a token. A token issued for one application profile must never activate another application.

The exact wire format should be versioned so future fields can be added without breaking older application versions. The profile's active public key set should be used to support key rotation per application.

## Instance Binding and Activation

A signed license proves that the portal issued the license, but it does not by itself prevent the license from being copied to another installation. Instance control requires an installation identity and activation records.

### Installation identity

Each application installation should generate a random installation ID on first startup and persist it in the application's data directory. The ID should be an application-generated UUID or equivalent random value, not a hardware fingerprint. Hardware fingerprints are fragile for containerized and Home Assistant deployments.

The application should also generate an instance key pair and keep the private key in its application data directory. The public key, key ID, and a proof signature can be exported as part of the customer-facing activation request. The private key must never be sent to the portal or displayed to the customer.

The application profile ID, installation ID, human-readable instance value, and instance public key should all be included in activation requests and, where appropriate, in the signed activation token.

### Activation flow

1. The application creates an activation request containing the application profile ID, configured instance value, installation ID, instance public key, and application version.
2. The application signs a portal-provided nonce or request digest with its instance private key.
3. The customer provides the activation request, plus the customer and payment information required by the portal.
4. The portal verifies that the request contains all profile-required fields and that the instance proof matches the public key.
5. The portal verifies that the license is valid and that the requested application profile matches the license.
6. The portal checks the license's installation limit and existing activations.
7. The portal records the installation and instance key as active.
8. The portal returns a signed activation token bound to the application profile, instance key, and installation ID.
9. The application accepts the token only when its signature, audience, expiration, instance binding, and local identity all match.

Example activation claims:

```json
{
  "license_id": "lic_12345",
  "app_id": "bartender",
  "installation_id": "instance_abc",
  "instance_key_id": "instance-key-abc123",
  "instance_public_key_sha256": "base64url-hash",
  "activation_id": "activation_789",
  "issued_at": "2026-09-13T00:00:00Z",
  "expires_at": "2026-10-13T00:00:00Z",
  "key_id": "bartender-signing-2026-01"
}
```

### Installation limits

The portal must enforce activation limits per license. For example:

```text
License: lic_12345
Installation limit: 2

instance_abc: active
instance_xyz: active
```

A new installation should be rejected when the limit is reached unless an existing activation is deactivated or an administrator resets the activations.

### Replacement and recovery

Customers need a supported way to move an application to a new Home Assistant installation or restore from backup. The portal should provide:

- Deactivate one installation
- Activate a replacement installation
- Reset all activations
- Administrator-assisted activation reset
- A self-service reset cooldown to prevent abuse

The application's installation ID should be included in backups carefully. Restoring a backup to a new host can either preserve the identity, treating it as the same installation, or generate a new identity and require reactivation. This policy must be explicit in the application integration documentation.

### Offline limitations and activation leases

An entirely offline license cannot reliably prevent copying. A customer could copy the license, installation ID, and application data directory together, making the clone appear identical to the original.

The recommended balance is:

- Paid license signature validation works offline after activation.
- Initial activation requires internet access.
- The portal records the installation ID and activation ID.
- The application periodically renews a signed activation lease, such as every 30 days.
- A short offline grace period, such as 7 days, allows for portal outages or temporary connectivity loss.
- Trial activation may require online contact to reduce trial-reset abuse.

This provides practical copy prevention without making the application unusable during a short licensing-service outage. It is stronger than offline-only validation while avoiding fragile hardware binding.

## Trial Licensing

The default trial is a 30-day signed trial license.

### Trial rules

- The trial starts on explicit activation or first completed setup, based on the product decision.
- The trial grants all Pro features.
- The token contains `license_type: trial` and an expiration timestamp 30 days after issuance.
- The application shows the remaining trial days.
- After expiration, the application falls back to Base limits without deleting Pro-created data.
- A paid license can be activated during or after the trial.
- A customer should receive one trial per customer or installation according to the commercial policy.

### Clock and availability considerations

A fully offline trial cannot completely prevent system-clock rollback. The application may record the last trusted timestamp and detect obvious rollback, but strict enforcement requires online activation.

Recommended compromise:

- Paid licenses validate offline.
- Trial activation may require one online request.
- Paid renewal may use occasional online contact.
- Allow a short offline grace period, such as 3 to 7 days, for renewal and service outages.

## Portal Responsibilities

The portal owns:

- Application profiles and profile versions
- Customer records
- Orders or subscription references
- License issuance
- Trial issuance
- License expiration
- Renewal
- Revocation
- Activation counts
- Installation limits
- Feature entitlements
- Payment-provider webhook processing
- Administrative audit events

Licenses must always reference an application profile. A customer may have licenses for several applications, each with independent plans, trials, activations, and expiration dates.

The portal should not store raw license tokens when a token hash and license metadata are sufficient.

## Portal API

Initial endpoints could include:

```text
GET  /v1/app-profiles
POST /v1/app-profiles
GET  /v1/app-profiles/{app_id}
POST /v1/app-profiles/{app_id}/keys/rotate
POST /v1/trials
POST /v1/licenses
POST /v1/license-requests/validate
GET  /v1/licenses/{license_id}
POST /v1/licenses/{license_id}/renew
POST /v1/licenses/{license_id}/revoke
POST /v1/activations
POST /v1/activations/{activation_id}/deactivate
POST /v1/webhooks/payment-provider
GET  /v1/health
```

The issuing, revocation, customer-management, and profile-management endpoints must require administrator authentication. The public activation endpoint should require an application ID/profile audience, be rate-limited, and should not expose customer data.

## Admin Interface

The private admin interface should support:

- Create and manage application profiles
- Configure plans, features, limits, trial duration, and installation rules per profile
- Manage profile-specific signing keys and public-key rotation
- Search customers
- View payment and license history
- Issue a trial license
- Issue a paid license
- Validate an instance activation request before issuing a license
- Renew a license
- Revoke a license
- Replace a license
- View activations and installation limits
- Deactivate an installation
- Rotate signing keys
- View audit events

For the first version, a protected CLI may be sufficient. Add the web admin interface when manual operations become frequent.

## Licensed Application Integration Requirements

Each licensed application should eventually contain:

- The public verification key or a trusted key set
- Its stable application ID and expected token audience
- License parsing and signature verification
- Local license storage in its application data directory
- Trial and paid expiration checks
- Centralized entitlement checks
- A Licensing section in Settings
- License activation and replacement UI
- Current plan and expiration display
- Base fallback behavior after trial or license expiration

An application's local product-profile setting must not be treated as proof of licensing. It should be replaced or supplemented by a centralized entitlement service backed by verified license state.

Each application should continue to operate in Base mode if the licensing portal is unavailable. Application-specific API token authentication must remain separate from licensing validation.

## Security Requirements

- Keep the Ed25519 private key outside all public repositories.
- Store signing keys in a secret manager or protected environment secret.
- Include a `key_id` in every token to support key rotation.
- Allow the application to trust the current and previous public keys during rotation.
- Never trust a plan or feature flag supplied only by the client.
- Validate signatures before reading entitlement claims.
- Validate expiration and not-before timestamps.
- Rate-limit activation and public license lookup endpoints.
- Authenticate all administrative operations with MFA where available.
- Keep payment webhook processing idempotent.
- Do not log raw license tokens or payment secrets.
- Minimize stored personal and device information.
- Document customer data retention and deletion behavior.

## Billing Provider Choice

### Stripe

- No monthly fee for basic use
- Flexible payment links and webhooks
- Requires more custom licensing workflow
- Good choice when control and API flexibility matter

### Lemon Squeezy

- Convenient for digital products and tax handling
- Higher transaction fees
- Less custom control than Stripe
- Good choice when minimizing payment operations matters

### Paddle

- Strong merchant-of-record capabilities
- Useful for global tax and compliance handling
- More expensive and operationally heavier for an MVP

The first implementation can use Stripe Payment Links or Lemon Squeezy with manual issuance. Automate webhooks after the license model is proven.

## Implementation Phases

### Phase 0: Product Decisions

- Register each application profile and finalize its Base and Pro feature matrix.
- Define profile-specific plans, limits, trial duration, and supported application versions.
- Choose whether trial starts automatically or by explicit user action.
- Choose trial-per-customer versus trial-per-installation policy.
- Define paid license terms and installation limits.
- Choose billing provider.
- Define support, refund, and revocation policies.

### Phase 1: Offline Issuer

- Generate and protect an Ed25519 key pair.
- Create an application profile and bind its token audience to the application ID.
- Build a private issuer CLI.
- Define and version the signed token format.
- Define the required instance-information contract for each application profile.
- Require an application-generated instance key and proof during license requests.
- Add local verification to one pilot application.
- Add local license storage and Base fallback.
- Add 30-day trial token support.

### Phase 2: Application UI

- Add Licensing settings page.
- Add token activation and replacement.
- Show Base, Trial, or Pro status.
- Show expiration and remaining trial days.
- Add centralized feature checks.
- Repeat integration for each supported application profile.

### Phase 3: Hosted Portal

- Add customer and license database.
- Add admin authentication.
- Add issue, renew, revoke, and activation APIs.
- Add payment webhooks.
- Move signing operations behind protected service boundaries.

### Phase 4: Automation

- Automate paid license issuance after successful payment.
- Add renewal handling.
- Add activation-limit management.
- Add email delivery.
- Add optional online trial activation and paid renewal checks.

## Acceptance Criteria

- A valid signed paid license enables only its claimed features.
- A license for one application profile cannot activate another application.
- Each application profile can define its own plans, features, limits, and trial policy.
- An activation token is bound to one application profile and one installation ID.
- License issuance requires the profile-required instance information and a valid instance proof.
- A BarTender license request includes the brewery name and unique instance key generated by that installation.
- The private instance key is never sent to or stored by the portal.
- Installation limits prevent unauthorized additional active instances.
- Customers can deactivate or reset an installation without losing their license.
- Paid licenses continue working during the documented offline grace period.
- An invalid or tampered token is rejected.
- An expired trial falls back to Base behavior without data loss.
- A paid license validates while the portal is unavailable.
- A revoked license follows the documented revocation/grace policy.
- Trial issuance is limited according to the chosen policy.
- Duplicate payment webhooks do not create duplicate licenses.
- Installation limits are enforced.
- Signing keys can be rotated without invalidating all existing licenses.
- No private signing key or payment secret is present in the application repository.
- Automated tests cover token signing, verification, expiration, tampering, trial rules, revocation, and webhook idempotency.
